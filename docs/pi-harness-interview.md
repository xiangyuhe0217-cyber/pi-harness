# pi-harness 项目面试手册（自然表达版）

这份文档不按源码路径讲，而是按项目负责人在面试现场会怎么讲。先给简历版，再给一到两分钟介绍，然后按评测、策略回放、记忆、工具治理、用户端、恢复与上下文逐层回答，最后是选型对比、最容易被追问的点，以及当前真实状态。

需要先说明一个原则：这个项目现在三条链路都已经完成骨架和测试，完整运行链路和本地评测已经跑通；但外部大规模数据还没有全部跑完。下面不会把“代码已经写好”说成“结果已经证明”。

## 一、简历版

**项目简介**

pi-harness 是面向 AI Agent 的运行时框架。它在 pi coding agent 外面加了一层工具网关、步骤级评测、策略回放、长期记忆和 Web 对话与调试界面，让 Agent 的每一步可观测、可管控、可调优。项目包含七条正常任务、十三条攻击用例、三轮策略迭代，以及 OpenViking 记忆同步闭环。

**技术栈**

Python、pi、LiteLLM、MCP、Docker、JSONL、OpenViking、DeepSeek、阿里百炼向量模型，以及原生 Web 前端。

**个人职责**

我负责 pi 运行时的接入和工具治理，把 pi 的内置工具关掉，让所有文件和命令操作都经过统一的工具网关，并实现路径、命令、注入和 secret 检查，以及带规则编号和策略版本的审计。

我负责步骤级评测，把模型回复、工具调用和工具结果归一成步骤事件，输出判定、归因、重复动作、上下文和预算指标，并把结果拆成快速通过、慢速通过、预算失败、能力失败和模型服务失败。

我负责策略回放和调优闭环，先在旧轨迹上重算策略决策，再用真实运行复现，最后用门控决定保留还是回滚。Prompt 的改动则必须真跑对照，不能只靠离线回放。

我负责长期记忆，包括写入策略、隔离审核、失败轨迹抽取经验、按仓库作用域隔离，以及和 OpenViking 的写入与审核后同步。

我负责用户端和调试台，让普通用户可以进行正常对话，让开发可以查看任务结果、执行审计和记忆审核队列。

**技术亮点**

十三条攻击用例的结果是零成功，十一条被工具网关拦截，两条是模型自己拒绝；正常任务七条全部通过。这里我不会把模型拒绝算成网关的功劳。

策略第二轮在旧轨迹上解开了一个误拦，攻击轨迹上没有出现从拦截变成放行的情况；真实运行复现三次都是全部通过。正常任务里被工具策略拦下的调用比例是二十九次中的两次。

Prompt 调整里，B 版成本上涨但通过率没变，被回滚；C 版在长任务上把 token 降低了超过一半，同时通过率没有下降。

长期记忆已经接入真实的 OpenViking 服务，审核通过后可以写入、读取和检索，仓库作用域会映射到对应目录；记忆相关测试已经覆盖写入、隔离、审核、冲突和注入。

上下文压力测试在小窗口下触发了两次压缩，利用率超过一，但这只是压力测试，不是生产分布。

**一句话**

pi 负责把活干了，我负责让每一步看得见、管得住、调得动。

## 二、一到两分钟项目介绍

pi-harness 是我给 pi 做的一层运行时框架。它解决的不是“再做一个 Agent”，而是 Agent 工程里三个更实际的问题。

第一，工具不可控。pi 本身有内置工具，如果只靠提示词或者普通回调，很难保证所有操作都被拦住。所以我把内置工具关掉，只保留工具网关，在路径、命令、注入和敏感信息这些位置做确定性拦截。

第二，失败不可解释。正常任务只给通过或者失败不够，我把模型调用、工具调用和工具结果都采集下来，输出判定、归因、重复动作、预算和上下文指标，再把结果拆成几类，避免把模型能力、预算不足和外部服务故障混在一起。

第三，调优不可回放。策略变化可以拿旧轨迹重新算决策，但新策略会不会诱导新行为，必须真实运行验证。Prompt 改动更是只能真跑，所以我们做过 B 版回滚和 C 版保留。

在这些之上，我还做了长期记忆。Agent 写进来的内容默认隔离，人工审核通过后才写进 OpenViking，避免错误经验或者恶意内容直接进长期记忆。

这个项目现在三条链路都已经有代码和测试，本地也跑通了正常任务、攻击任务和记忆任务。但外部大规模评测、自动 Prompt 优化和大规模记忆评测还没有全部跑完，所以我不会把当前状态说成完整平台。

## 三、完整链路

一条任务运行是这样走的。用户提交任务后，运行编排先创建一个独立的运行目录，把初始工作区复制进去，绑定策略版本和记忆范围，然后启动 pi。模型请求走 LiteLLM，工具请求走工具网关。网关先做路径、命令、注入和敏感信息检查，再执行文件或者命令操作，并把每次允许和拦截写入审计。pi 的原始事件被采集层归一成步骤事件，任务断言检查文件和测试，分析层再计算重复动作、无进展、衰减、预算和上下文，最后输出判定、归因、结果分类、证据和报告。

用户端对话是另一条链路。每个聊天会有一个独立的工作区和独立的 pi 会话，第一条消息创建会话，后续消息延续同一个会话；工具调用同样经过网关，回复里会显示工具数量和拦截数量。聊天目前是同步返回，没有做流式输出。

记忆审核是第三条链路。用户或者 Agent 写入一条记忆后，先进入隔离队列；人工审核通过，本地状态变成可用，再同步写入 OpenViking；同步失败会记录状态，可以重试。审核拒绝就只在本地标记拒绝，不写远端。

## 四、整体设计拷打

**为什么不是又一个 Agent**

pi 已经有循环、上下文压缩、工具、会话和恢复能力。我不重写这些，我补的是 pi 没有的部分：工具治理、策略和审计、步骤评测、策略回放、长期记忆和用户界面。我的价值不是写一个更聪明的循环，而是让循环可观测、可控制、可调优。

**这个项目最难的部分是什么**

最难的是边界。工具能力和安全边界怎么划，预算失败和能力失败怎么分，离线回放和真实行为怎么分，Agent 写入和人工审核怎么分。每一层如果边界不清楚，最后都会变成“看起来合理但业务上不闭环”。第二个难点是证据链，模型说了什么、用了什么工具、依据是什么、失败在哪里，都要能还原。

**数据分别放在哪里**

每次运行都有独立的运行目录，里面有原始事件、归一化事件、工具审计、结果、报告和恢复状态。长期记忆在本地有一个可审计的存储，审核记录单独保存。最终记忆会同步到 OpenViking。聚合评测结果会单独保存，原始运行数据不提交到代码仓库。

**AI 辅助开发下，你的价值在哪里**

AI 能快速给实现，但不会替我决定为什么用工具网关而不是普通回调，为什么判定用规则而不是大模型评审，为什么回放只对旧轨迹，为什么 Agent 写入必须隔离，为什么 Docker 镜像验证了但运行编排还没接。我的工作是提出这些约束，再用真实代码和失败路径验证 AI 的输出。

**当前最大的不足**

样本小，七条正常任务和十三条攻击只能证明链路，不是统计结论；外部基准还没有真正跑完；Docker 镜像验证过但默认运行还在宿主环境；OpenViking 当前没有鉴权；步骤判定和归因主要还是规则，语义判断不够。

## 五、步骤级评测

**评测做了什么**

第一层是任务级评测。正常任务用文件和测试做断言，攻击任务用是否被拦截、有没有副作用、有没有泄露做断言。第二层是步骤级评测，把一次模型回复、一次工具调用、一次工具结果分别采集下来，计算重复动作、无进展、衰减、失败调用、拦截调用、预算和上下文。第三层是结果分类，把通过拆成快速通过和慢速通过，把失败拆成预算失败、能力失败和模型服务失败，把攻击结果拆成被拦截、模型拒绝和攻击成功。

**解析粒度是什么**

我按三种粒度采集。一次模型回复是一条模型事件，一次工具调用是一条工具事件，一次工具结果是一条结果事件。模型回复才推进步骤号，同一步里可以有多条工具调用。这样既能看模型做了几轮，也能看每轮用了哪些工具。嵌套的代码执行会产生外层和内层工具事件，所以工具审计里的拦截数和步骤汇总里的拦截数可能不完全一样，做策略分析时我会以审计为准。

**为什么没有用大模型评审**

因为当前阶段要的是确定性、可回放和低成本。判定主要靠规则：重复动作、无进展、衰减、拦截、预算、攻击副作用和泄露。准确性靠任务断言和攻击断言保证。归因做过一次作者人工标注的小样本一致性检查，二十二条一致，但这不是独立双人标注，也不是统计显著结论。之前还出现过把“断言实现而不是行为”误判成编辑失败的情况，那是测试断言的问题，不是模型能力问题。

**归因怎么设计**

攻击先看有没有副作用或者泄露，有就是绕过，没有但被拦就是安全拦截，既没绕过也没被拦就是模型拒绝。正常任务先看预算，再看循环，再看失败调用，再看重复动作，再看拦截，最后才看是通过、环境错误、定位问题还是编辑问题。它是一套有优先级的规则，不是大模型在自由判断。

**重复动作和上下文指标包含什么**

重复动作看相同的工具和参数出现了多少次；无进展看文件有没有变化而步骤已经不少；衰减看后半段的 token 是不是明显高于前半段；循环看重复次数或者无进展；浪费看重复和失败调用。上下文看最大输入、窗口大小、利用率、是否超过警戒线、压缩次数和每次压缩前的 token。上下文丢失率没有直接测，现在只有利用率和压缩次数这些代理指标。

**结果分类为什么要分五类**

只报通过率会把预算不足、模型能力不足和外部服务故障混在一起。快速通过和慢速通过都是通过，但效率含义不同；预算失败说明多给资源可能就过了；能力失败说明在预算内确实没做出来；模型服务失败不是模型或者框架的问题，应该从分母里排除。攻击则单独用安全拦截、模型拒绝和攻击成功来统计。

**这个评测完整吗，闭环了吗**

不完整。策略层和 Prompt 层有局部闭环，但外部基准、统计检验、上下文丢失率和生产流量都没有。现在三条链路已经有代码和测试，本地正常任务、攻击任务和记忆任务也跑过；但 SWE-bench 的十二乘二真实运行、自动 Prompt 优化和 LoCoMo 记忆评测还没有跑完，所以只能讲链路和设计，不能讲大规模结论。

**和开源评测项目相比怎么样**

SWE-bench 是标准化的真实代码修复评测，样本大、判定标准明确；我们只有七条自建任务，不能直接比较。Inspect AI 是通用评测框架，数据集和指标生态更完整；我们的优势是运行时集成、工具审计和策略回放，不是评测框架本身。AgentBench 覆盖多环境，我们只做代码沙箱。AgentDojo 这类安全评测有标准注入攻击，我们的十三条攻击是自建的，覆盖有偏差。

我们的优势是能把工具拦截、步骤判定、策略回放和记忆审核放在同一条链路里看；劣势是样本小、非标准、没有 held-out、没有统计显著性，也没有完整的外部基准结果。

**怎么对齐开源评测标准**

需要固定数据集版本和运行环境，多次运行并给出置信区间，把调优集和留出集分开，接入至少一个外部基准，校准语义评审，建立回归流水线，发布原始轨迹、预测和报告，最后把安全和能力分开报告。我们现在已经有外部基准适配和本地测试，但真实数据还没跑完。

## 六、策略回放与 RSI

**策略迭代是怎么驱动的**

第一轮是严格基线。第二轮是因为正常任务里有一个带错误输出合并的命令被误拦，这是过度拦截，所以放开这一类写法。第三轮不是线上失败驱动，而是威胁模型驱动，把包安装模块禁掉，收紧供应链风险。每一轮都先在旧轨迹上回放，再看真实运行。

**回放怎么保证环境一致**

回放不重新调用模型，只拿旧轨迹里的工具调用，用新策略重新判断允许还是拦截，所以模型温度、随机性和上下文生成都不会影响它。它保证的是策略决策可重算，不是 Agent 行为可复现。旧轨迹里的工作区是运行结束后的状态，文件内容扫描可能受后续写入影响；命令输出也不会重新执行。所以回放只能看旧操作，不能证明新策略不会诱导新行为。新行为必须靠真实运行覆盖。

**Prompt B 和 C 怎么解释**

B 版加了“先跑测试、别用管道”这类通用要求，结果通过率没变，token 和成本反而涨了三成多，所以回滚。C 版不是改系统提示词，也不是改历史截断，而是针对长任务加了一条很具体的指令：大文件只读一次，先记笔记再写摘要，不要修改原文件。它把重复读和无效工具调用压下去了，token 降了一半多，通过率没有下降。它不一定能泛化到所有任务。

**A/B 的置信度怎么算**

当前没有统计置信度。六条任务、每条一次，只能做成本门控：没有通过收益、成本明显变差就回滚。策略复现三次全部通过也只是稳定，不是百分之百置信。严格做法应该是同一任务成对跑多次，算通过率差值的置信区间，再用留出集验证。

**这是完整的 RSI 吗**

不是。当前是人工在环的证据门控迭代：人看失败和审计，人写策略或者 Prompt，回放或者真跑验证，人决定保留还是回滚。没有自动发现、自动提案、自动搜索和自动改代码。后来补了自动 Prompt 优化的适配和留出门控，但真实优化还没有跑完，所以不会说成完整 RSI。

**为什么选择 Prompt 优化，不选自改代码或者进化搜索**

自改代码需要强沙箱、完整验证和回滚，当前不安全；进化搜索的搜索空间和算力成本都高，也容易过拟合。Prompt 优化只改一个文本参数，和现有评测直接对接，失败可以回滚，是当前最稳的一条链路。

## 七、长期记忆与 OpenViking

**记忆做了什么**

本地记忆有作用域、类型、键、正文、来源、置信度、过期时间和状态。Agent 和工具写进来的内容默认进入隔离状态，不允许直接变成可用记忆。注入、敏感信息、超长内容会直接拒绝；相同键出现冲突会隔离；完全重复会去重；过期会失效。人工审核通过后才变成可用，拒绝就只保留拒绝状态。失败轨迹可以按规则抽出一条经验，但同样先进入隔离队列。

**作用域隔离怎么实现**

每条记忆带作用域，检索和审核都按作用域过滤，工具网关和运行编排会把当前作用域传下去，同步到 OpenViking 时也会映射到对应目录。但这是逻辑隔离，不是权限隔离：所有记录还在同一个本地文件里，OpenViking 当前也没有开鉴权，所以不能说成安全边界。

**失败轨迹抽经验有没有用大模型**

没有。现在是根据失败结果和工具审计拼一条规则化的经验，比如超时、预算、被哪些规则拦住、重复动作、测试失败。它不会自由发挥，但也不做反事实验证。真正防止错误经验固化的是隔离、人工审核、冲突检测和过期，而不是抽取本身。

**OpenViking 怎么接的**

审核通过后写 OpenViking，正文带作用域、类型、键、来源和置信度，目录按作用域映射，标签也带作用域和类型。读取和检索走 OpenViking 的记忆检索，检索结果可以回到原始正文。当前已经用真实服务验证过写入、读取和检索，检索分数大约零点九；仓库作用域也验证过映射。但当前是开发模式，没有鉴权，没有多租户，拒绝也不会删除远端记录。

**记忆链路完整吗**

写入、审核、同步这条闭环是通的；自动抽取、自动合并、语义召回和大规模评测还不完整。最近补了用 OpenViking 会话做候选抽取、隔离审核、再写正式库，以及上下文召回和 LoCoMo 风格评分的代码，但真实 staging 服务和数据还没有跑完。

**和 Mem0、Letta、Zep 这些系统比**

召回质量、自动抽取和规模上没有优势。它们有成熟的自动抽取、合并、向量或者图谱检索；我们现在是关键词检索为主，自动抽取能力弱，规模也小。我们唯一的差异是写入治理：Agent 写入默认隔离，注入和敏感信息拦截，人工审核，审计和作用域隔离。这个差异适合高风险场景，不代表记忆质量更好。

## 八、工具网关与安全

**工具网关的设计难点**

难点不是写一个服务，而是让所有工具都必须经过它，并且能解释每次决策。pi 要关闭内置工具，只保留网关工具；网关要统一文件和命令能力，做路径解析、工作区边界、命令白名单、禁止管道和重定向、禁止任意脚本执行、限制写入大小、扫描注入和敏感信息；每次允许和拦截都要写规则和策略版本。还要处理嵌套代码执行、超时、环境变量清理和工具结果扫描。

**怎么防止恶意调用**

路径上先解析真实路径，再检查是否还在工作区，符号链接指向外部也会被拦住；命令上只允许白名单二进制，不允许管道、重定向和任意脚本；写入有大小上限；工具输出再扫注入和敏感信息；所有决策都有审计。它防的是工具层的确定性攻击，不是模型层的所有语义攻击。

**Docker 到底怎么做的**

Docker 镜像做过验证，是非 root、限制网络、带资源限制的镜像。但当前默认运行编排还在 WSL 宿主里起 pi 进程，并没有把每次运行都放进容器。所以面试时不能说自己已经实现了全容器隔离运行，只能说镜像和隔离方案验证过，默认开发路径还在宿主。真正生产化要把运行编排接到容器，并补资源限制和逃逸测试。

**超时和死循环怎么处理**

单次命令有超时上限，任务有总超时，超时会杀进程。但没有在线的死循环检测和资源配额，只有事后根据重复动作、无进展和衰减来判断循环和浪费。真正生产化需要容器级 CPU 和内存限制，以及运行中的终止策略。

**十三条攻击是自建还是业界基准**

全部是自建，没有直接用 PromptInject 或者 OWASP 的基准集。覆盖路径穿越、符号链接、危险命令、外网访问、敏感文件、SSH、提示注入、直接读系统文件、内联代码、全盘搜索、管道外传和记忆投毒。结果是十一条被拦，两条模型自己拒绝，零条成功。这个结果只能说明这批用例和当前模型下的链路有效，不能外推成通用安全。

## 九、用户端、调试台与鉴权

**为什么做两个界面**

用户端就是一个正常的 Agent 对话框，面向体验；调试台面向开发和调试，可以跑任务、看步骤、看工具审计、审核记忆、抽经验。两个界面共用一个本地服务，但职责分开。

**聊天链路怎么走**

每个聊天有独立的工作区和独立的 pi 会话，第一条消息建立会话，后续沿用同一个会话；工具调用同样经过网关，回复里会显示用了多少工具、被拦了多少次。聊天目前没有流式输出，是同步返回。

**鉴权开了吗**

Harness 的 Web 服务支持可选的访问令牌，设置后接口需要携带令牌，页面首次访问会提示输入；但当前实例默认没有开启。OpenViking 现在是开发模式，没有鉴权，也没有多租户。所以不能说“完整鉴权已经做完”。

**为什么用原生 Web 而不是前端框架**

这是本地调试和演示优先的选择，不引入 Node 和 TypeScript，部署简单。产品化需要换成正式前端框架，并补登录、权限和会话管理。

## 十、恢复与上下文

**恢复怎么做**

每次运行会保存任务、工作区、会话目录、策略、模型和状态。运行被中断后，可以找到最新的 pi 会话，让它继续，再重新采集、重新断言、重新分析。之前用三秒超时杀过一个任务，恢复后任务通过，说明会话和元数据这条恢复链路是通的。但恢复依赖 pi 会话已经落盘，会话没落盘就恢复不了。

**上下文指标怎么测**

上下文指标看最大输入、窗口大小、利用率、警戒线、压缩次数和每次压缩前的 token。小窗口压力测试下触发了两次压缩，利用率超过一；但这是压力测试，不是真实一千多 k 窗口的自然分布。

**上下文丢失率怎么测**

没有直接测。现在只有利用率和压缩次数这些代理指标。要做真正的丢失率，需要在任务里放一个必须记住的约束，在压缩前后各问一次，统计压缩后约束通过率，再按利用率分桶比较。

## 十一、选型对比

Agent 底座选 pi，而不是自研。因为循环、上下文压缩、会话和恢复这些能力 pi 已经比较完整，自研会把大量时间花在重复造轮子上。代价是依赖 pi 的事件格式和稳定性。

模型网关选 LiteLLM，而不是自己写转发。因为路由、日志和预算这些能力可以复用，Harness 专注工具治理和评测。代价是回调能力受网关限制。当前开发环境里 LiteLLM 启动被远程成本表拉取卡住，所以本地临时用了一个轻量转发兜底，但设计上仍然以 LiteLLM 为主。

工具治理选关闭内置工具、只走网关，而不是保留内置工具再加回调。因为内置工具可以绕过回调，只有把入口收窄，拦截才是确定的。代价是所有工具能力都要自己补。

沙箱选 Docker 镜像验证，但默认运行还在宿主。这是当前开发阶段的取舍，生产必须接容器。

评测选规则判定和任务断言，而不是一上来用大模型评审。因为规则便宜、确定、可回放；大模型评审适合语义判断，但需要校准，当前没有。

RSI 选人工在环的策略回放和 Prompt 对照，而不是自动改代码或者进化搜索。因为当前最需要的是可解释、可回滚，而不是最大化搜索。

记忆选本地可审计存储加 OpenViking 同步，而不是直接上 Mem0 或者纯向量库。因为当前最需要的是写入治理和审核，召回质量不是第一优先级。代价是召回能力弱、自动化程度低。

Web 选原生实现，而不是前端框架。因为当前目标是本地调试和演示，不是产品级前端。

鉴权选可选访问令牌，而不是完整多租户。因为当前是本机单用户；生产化必须补。

## 十二、最容易被追问的十个点

第一个，零成功不等于十三条都被网关拦住，实际是十一条拦截、两条模型拒绝，不能把模型拒绝算成网关能力。

第二个，判定不是大模型评审，而是规则加任务断言；人工一致性只是小样本检查，不是准确率证明。

第三个，回放不能复现 Agent 行为，只重算旧工具调用的策略决策；新行为必须真实运行。

第四个，Docker 镜像验证过，但默认运行还没进容器，不能说自己完成了全容器隔离。

第五个，Harness 的鉴权只是可选令牌，OpenViking 是开发模式，没有多租户。

第六个，记忆召回没有大规模基准数据，只有真实 OpenViking 的单条写入、读取和检索验证，以及 LoCoMo 评分的代码。

第七个，正常任务七条和攻击十三条都是自建小样本，不能外推成模型能力或者通用安全。

第八个，这个项目是运行时框架，不是 CRUD 后台，所以没有用 Spring、MySQL、Redis 那一套；本地存储优先保证可审计，生产化再换。

第九个，评测只在策略和 Prompt 层有局部闭环，完整能力评测、统计检验和上下文丢失率还没有。

第十个，AI 帮我加速了实现，但边界是我定的：工具网关、规则判定、旧轨迹回放、Agent 写入隔离、Docker 还没接运行，这些都是我判断和验证的结果。

## 十三、当前真实状态

三条链路的代码和测试已经完成。评测链路有外部基准的适配、任务准备、补丁提取、官方评测调用和报告；记忆链路有 OpenViking 会话抽取、隔离候选、审核、正式写入、上下文召回和记忆评分；RSI 链路有 Prompt 优化适配、开发集、留出集和门控。测试层面，记忆相关十四条、评测相关三条、RSI 相关五条，共二十二条全部通过。

本地 WSL 里已经实际跑过正常任务、攻击任务和记忆任务：正常任务通过，符号链接攻击被拦，记忆任务通过。Web 服务和 OpenViking 也已经启动过。

但真实外部数据还没有全部跑完：SWE-bench 的十二乘二还没有正式运行，自动 Prompt 优化还没有真正优化，LoCoMo 记忆评测还没有出结果，记忆 staging 也还没有跑完整批数据。所以当前最准确的表述是：三条链路的骨架、测试和本地闭环已经完成，外部大规模结果还在待跑。

## 十四、最后一页

一句话：pi 负责把活干了，我负责让每一步看得见、管得住、调得动。

三个数字：十三条攻击零成功，其中十一条拦截、两条模型拒绝；策略第二轮真实复现三次全部通过；长任务 Prompt 调整把 token 降低超过一半且通过率不降。
