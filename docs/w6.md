# W6：Prompt C + 小窗口 Compaction + OTel 导出

## 1. Prompt C：针对 C001 的效率调优

C001 基线：读 154KB 日志写摘要。

| 版本 | steps | tools | tokens | cost | repeated read | verdict |
|---|---|---|---|---|---|---|
| 基线 | 10 | 22 | 35,490 | $0.002698 | 3 | wasteful |
| Prompt C | 6 | 7 | 17,920 | $0.001534 | 0 | ok |

Prompt C：

> Do not read large.txt more than once. Read it once, take notes, then write summary.txt. Do not modify large.txt.

结论：

- tokens **−49%**，tools **−68%**，重复读 **3→0**。
- W8 复测：7 steps / 9 tools / 16,489 tokens / 重复读 2 / **SlowPass**；重复读有波动（一次 0，一次 2），但 pass 不掉。
- 对比 W5 的 Prompt B（+37% tokens、pass 不变），说明 **prompt 要有针对性假设**，泛泛地“先跑测试”只会增加成本。

## 2. 小窗口 Compaction

为了真正触发 pi 的自动压缩，不动全局配置，而是复制一份临时 pi home：

- `contextWindow: 3500`
- `compaction.reserveTokens: 2000`
- `compaction.keepRecentTokens: 1000`
- `PI_OFFLINE=1`，避免模型目录刷新覆盖窗口。

结果（C001-small）：

| 指标 | 值 |
|---|---|
| status | pass |
| steps / tools | 7 / 12 |
| tokens | 15,934 |
| max_input | 3,656 |
| context_window | 3,500 |
| utilization | **1.045** |
| anxiety | **true** |
| compaction_count | **2** |
| tokensBefore | 3,431 / 4,175 |

结论：compaction 和 context anxiety 都真实触发了；这不是改指标，而是把部署窗口调小后的真实行为。

## 3. OTel 导出

```bash
harness export --run <run_dir>
```

生成 `otel.json`（OTLP-style）：

- `traceId`：run_id 的 sha256 前 32 位；
- `spanId`：事件 seq；
- `parentSpanId`：tool 的父 span 指向 model_call；
- attributes：`harness.kind / step / verdict / tool / rule`、`llm.token_count.total`、`llm.cost_usd`、`llm.stop_reason`。

实测 C001-small 导出 **31 spans**，可直接投 Langfuse/OTel Collector（需要配置 endpoint）。

## 4. 本轮结论

- Prompt C 是正结果，Prompt B 是负结果；两者都要记录。
- 小窗口实验证明 compaction/anxiety 指标不是摆设。
- OTel 导出打通了“本地 Harness → 可观测平台”的路径。

## 5. 已知限制

- 小窗口是通过临时 pi home 模拟的部署配置，不是 131k 真实模型窗口下的自然 compaction。
- Prompt C 只验证了 C001 一条任务，泛化性需要在更多长任务上测。
- OTel 导出只是 JSON，不含真实上报；接 Langfuse 需要 endpoint 和鉴权。
