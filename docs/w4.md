# W4：Checkpoint/Resume + Policy Replay

## 目标

1. 中断可恢复：`run_state.json` + pi session。
2. 策略可回放：录制轨迹上重算策略决策，不调模型。
3. 3 轮迭代：p1 → p2 → p3，出对比表。

## Policy 版本化

- `policies/p1.json`：基线。
- `policies/p2.json`：允许 `2>&1`（执行前 strip 掉）。
- `policies/p3.json`：p2 + 禁用 `python -m pip` / `ensurepip`。

每个 run 的 `gateway_audit.jsonl` 都带 `policy` 字段；`result.json` 带 `policy`。

## Replay

`harness replay --run <run_dir> --policy policies/p2.json`

做法：

1. 读 `events.jsonl`。
2. 归一工具名（`mcp__harness__fs_read` → `fs_read`）。
3. 跳过 `codemode` 包装、未知工具、参数不完整的调用。
4. 对每条 `tool_call` 调 `decide(workspace, tool, args, policy)`，不执行。
5. 和旧的 `tool_result` 对比：`block->allow` / `allow->block` / 不变。

边界：

- `fs_read` 会重新读文件并扫注入/secret（否则会误判 block→allow）。
- `shell_exec` 的输出无法回放（需要旧结果）；只回放命令参数策略。
- 非策略类 block（如 `path.not_directory`）记为 `error`，不算策略 block。

## 回放结果

p2 作用在 p1 的 benign 轨迹：

```
allow->allow: 25
block->allow: 1
block->block: 2
```

- 1 个 `2>&1` 的 over-block 被解开。
- 2 个 `&&`/管道命令仍然被拦（有意保留）。

p2 作用在 p1 的 attack 轨迹：

```
block->block: 25
allow->allow: 17
error->allow: 1
```

- **没有 block→allow 的安全回退**；`error->allow` 是非策略类错误。

p3 作用在 p2 的 benign 轨迹：

```
block->block: 3
allow->allow: 23
```

- 没有新增 block；`pip` 禁用对现有调用无影响。

## 3 轮对比

| 轮次 | 策略改动 | 离线回放 | benign | ASR |
|---|---|---|---|---|
| R0 | p1 基线 | — | 6/6，audit block 3 | 0/12 |
| R1 | p2 允许 `2>&1` | benign: 1 block→allow；attacks: 0 block→allow | 6/6，audit block 3 | 0/12 |
| R2 | p3 禁 `python -m pip` | benign/attacks: 0 新增 block | 6/6，audit block 3 | 0/12 |

> 注意：live 的 audit block 数有噪声（模型每次写法不同），所以策略改动要靠 replay + 多次 trial 判断，不能只看一次 run。

## Checkpoint / Resume

每个 run 写 `run_state.json`：

```json
{
  "run_id": "...",
  "task_id": "T007",
  "task_file": ".../demos/T007.json",
  "workspace": "...",
  "session_dir": "...",
  "provider": "litellm",
  "model": "deepseek-chat",
  "policy": "p1",
  "mcp_only": true,
  "status": "running"
}
```

中断后：

```bash
harness resume --run runs/resume-demo2/T007-... --timeout 180
```

- 找最新 pi session 文件；
- `pi --session <file> -p "Continue..."`；
- 重新采集、断言、分析，写 `resume_result.json` / `resume_report.md`；
- `run_state.json` 更新为 `resumed`。

实测：T007 用 `timeout_s: 3` 被 kill，state=failed，但 session 已落盘；resume 后 **pass**，`changed_files=['calc.py','test_calc.py']`。

## 复盘：Replay 的三个坑

1. **工具名是外层名**：pi 事件里是 `mcp__harness__fs_write` / `codemode`，不是 `fs_write`。要归一 + 跳过包装。
2. **内容型 guard 不能只看参数**：`fs_read` 的注入/secret 要重新读文件，否则会把“因注入被拦”误判成“新策略放行”。
3. **非策略 block 不是策略 block**：`path.not_directory` 是执行错误，不是安全策略；要分开统计。

## 已知限制

- 上下文利用率仍低（~0.007），compaction=0；context anxiety 未真正触发。
- Replay 只覆盖策略层；prompt/工具描述/模型改动必须真跑。
- Resume 依赖 pi session；如果 kill 发生在 session 落盘前，无法恢复。
- 预算还没接 LiteLLM 实际 token/成本。
